# Building a 4004

The long arc: an Intel 4004 you can watch run, one device at a time. This
is the plan and the reasoning behind it, not a description of anything that
exists yet — today the repo has the device model and the gate library the
machine will be built from.

## Authenticity: what is real and what is deliberately not

Aim for the real architecture wherever it is tractable; drop only what was
forced by 1971 packaging. The distinction is worth stating because "we
simplified it" and "the real one worked this way" are different claims and
a reader deserves to know which they are looking at.

**Real, and built that way:**

- The instruction encoding. OPR in the high nibble, OPA in the low one,
  `1110`/`1111` escaping to a second-nibble opcode. Genuine 4004 bytes
  decode correctly.
- `ADD r` reads the register the instruction names, adds the accumulator
  and the carry flag, writes both back. That is the actual datapath, not an
  immediate-add shortcut.
- The carry flag as a one-bit register that ADD both consumes and produces,
  which is what lets a chain of ADDs carry across nibbles.
- A hardwired control unit — phase AND decoded instruction — because the
  4004 was hardwired rather than microcoded.
- 16 x 4 index registers, Harvard split, mask ROM as an NMOS array.

**Deliberately dropped, and why:**

- The multiplexed 4-bit bus and its 8-phase cycle. Those exist because
  Intel had sixteen pins; most of the phases shuttle a 12-bit address
  through a 4-bit port one nibble at a time. Honouring it would roughly
  triple the control-sequencing device count and teach packaging rather
  than architecture.
- PMOS. The real chip is entirely P-channel with dynamic registers, which
  is why it has a *minimum* clock frequency. Static CMOS is legible — a
  paused machine holds its state while you look at it — and the engine has
  no charge decay to model the alternative honestly.
- 4 KB of program space; the demo ROMs are eight words.

**Ours, not the chip's — say so when describing it:** the phase structure.
The 4004 runs eight phases (A1 A2 A3 M1 M2 X1 X2 X3), five of which exist
only to move a 12-bit address and an 8-bit instruction through a 4-bit bus
a nibble at a time. Dropping the multiplexed bus drops those, and what is
left needs a different decomposition rather than a subset: the machines
here run FETCH / DECODE / EXEC, or FETCH / DECODE / FETCH2 / EXEC once
two-byte instructions are honoured. The *reason* for a second fetch is
architectural — an operand must be read before it is used — but the shape
is not the real one, and a description that implies otherwise is wrong.

**Simplified for now, worth revisiting:** the demo machines use a 3-bit PC
against an 8-word ROM, so a jump reaches only eight addresses rather than
the real 12-bit space. Two-byte fetch has landed, so a jump's target is now
a genuine second byte; widening it needs the 12-bit program counter wired
in place of the 3-bit demo one.

## Scope: a 4004 architecture, not a pin-compatible 4004

Two things about the real chip should be dropped deliberately.

**The multiplexed 4-bit bus** — the A1/A2/A3/M1/M2/X1/X2/X3 time slots, the
two-phase clock, the 4001/4002/4003 companion-chip protocol. All of that
exists because Intel had sixteen pins to work with. Pin scarcity means
nothing here, and honouring it would roughly triple the control-sequencing
device count for no pedagogical gain.

**4 KB of program space** — see [Program store](#program-store).

Keep what actually *is* the 4004: the 4-bit datapath, accumulator and carry,
the 16×4 index-register file (pairable to 8 bits), a 12-bit program counter
with a 3-deep address stack, the Harvard split between program and data
memory, and the real instruction encoding, so genuine 4004 assembly runs.

### Why the 4004 and not the 8008

Earlier plans named the 8008. The 4004 is the better target: half the
datapath width, Harvard architecture (so program store can be a read-only
fixture rather than writable memory), no interrupts, and a 3-level stack
instead of 7. The existing `add4`, `reg4`, `addsub4` and `dec24` circuits
are already 4004-width building blocks. The 8008 after, if ever.

## What the device model changes

Three constraints that a relay-only machine could not escape are gone.

**Buses work.** In relay logic there is no tri-state and no wired-OR, so
every shared wire has to be a one-hot selection tree and every destination
needs its own multiplexer. Transistors give real tri-state — a transmission
gate or a tri-state inverter — so the 4004's internal bus architecture is
implementable as designed. That is a large cut in device count and it means
following the real schematic rather than inventing a mux-tree equivalent.
The `tristate` circuit is that mechanism on its own, including both ways it
goes wrong.

**ROM stops being the hard problem.** A bare switch matrix sneak-paths: the
selected row drives a bit line, and that line backfeeds through an
unselected row's closed switch and out again, lighting bits that are not in
the addressed word. Historically that is exactly why diode matrices existed.
A real mask ROM is an NMOS array — a transistor present at a site stores a
`0`, absent stores a `1` — with the row decoder driving isolated gates. No
sneak paths, structurally.

**RAM gets cheap — but not cheap enough to be worth building.** A 6T SRAM
cell would bring a real 4002's 320 bits down to roughly 2,600 transistors
from the ~7,400 the current latch-based cell would cost. Both are large
against a 2,300-transistor CPU, and neither teaches anything the register
file has not already demonstrated: storage is storage, and there is a
16×4 register file in the library built from real cells for anyone who
wants to see one.

So the 4002 is modelled behaviourally — the one place in this project a
circuit is not simulated, and allowed because it is a *separate chip*
across a bus rather than part of the CPU. See CLAUDE.md's fourth rule for
where that line sits. What is kept real is the part that is about the
4004: the SRC addressing, the DCL bank select, the port behaviour, and
the timing of when data appears. What is modelled is only the array of
nibbles behind them.

## Device budget

The 4004 is **2,300 transistors** — a documented figure, and a reachable
one. For comparison, a relay equivalent was estimated at ~600 relays and
~3,000 contacts: the same simulation order of magnitude, far less
authenticity.

Estimates below are the original budget. Where a block has been built, the
measured device count is in [INVENTORY.md](INVENTORY.md) rather than
repeated here. The register file came in about 3× its estimate — a
static latch plus a tri-state buffer per cell costs far more than the 6T
SRAM cell the guess assumed — so treat the remaining numbers as optimistic
and expect the finished machine to land above 2,300 devices unless the
storage blocks move to SRAM cells.

| Block | Devices |
|---|---|
| 16×4 index-register file + 4-to-16 decode | built — ~3× the estimate |
| Accumulator, carry, ALU input steering | ~120 |
| ALU (add / sub / AND / OR / XOR / shift) | built — ~2.7× the estimate |
| 12-bit PC + jump load | ~250 |
| 3-level address stack + stack pointer | ~350 |
| Instruction register + decode | ~250 |
| Timing ring counter + control gating | ~250 |
| Program ROM, 32–256 words × 8 | array-dominated, see below |
| Data RAM, 16 nibbles | ~400 |

The feasibility question is settled by precedent: visual6502 simulates a
real 6502 (3,510 transistors) at switch level in a browser, in JavaScript.

## Instruction set: what is built

45 defined instructions (three codes — 0xE3, 0xFE, 0xFF — are undefined on
the real chip and decode to nothing here either). Fifteen are wired into a
datapath; the decoder recognises all of them, which is why a program
listing can already disassemble anything.

**Done** — decoded, sequenced, and acting on hardware:

| | |
|---|---|
| `LDM` | load immediate into the accumulator |
| `ADD` | accumulator + register + carry, result and carry back |
| `XCH` | write-only so far: accumulator → register, no read back |
| `INC` | decoded and gated; the register increment path is not built |
| `JUN` | unconditional jump, target from a real second byte |
| `JCN` | conditional jump; full 4-bit mask, TEST pin included |
| `IAC` | increment: the adder fed the constant 1 |
| `DAC` | decrement: the adder fed 15, and carry means *no borrow* |
| `CMA` | complement — four inverters into the accumulator's mux |
| `RAL` | rotate left through carry |
| `RAR` | rotate right through carry; `RAL`+`RAR` is the identity |
| `CLB` | clear both — select no mux source and the result is zero |
| `CLC` | clear carry |
| `STC` | set carry |
| `CMC` | complement carry |

`TCC`, `TCS`, `DAA` and `KBP` are decoded and have their control lines, but
are not yet given datapath results: `TCC` needs the carry to reach the
accumulator, and `DAA`/`KBP` are small lookup tables rather than adder
steering, so they belong in a block of their own.

The economy is the point. Thirteen instructions cost one extra decoder
(the same 4-to-16 block used three times already, now a fourth), three
mux terms and a handful of OR gates — because `IAC`, `DAC` and `TCS` are
all *the existing adder fed a different constant*, and `CMA`/`RAL`/`RAR`
are wiring rather than logic.

**Next, roughly in dependency order:**

1. **`SUB`** — the adder is there; subtract is add-the-complement with the
   carry inverted, which is the `addsub4` circuit's trick one level up.
2. **`LD`, and `XCH` reading back** — the register file already reads; the
   accumulator needs a path from it. `XCH` is a genuine swap and needs both
   directions in one instruction.
3. **`TCC`, `DAA`, `KBP`** — the four accumulator instructions left over.
   `TCC` only needs the carry routed into the accumulator's mux; `DAA` and
   `KBP` are small tables and want their own block.
4. **`ISZ`** — increment a register and jump if the result is not zero.
   Needs the register increment path and reuses the condition tree.
5. **Memory group** against the modelled 4002 (`SRC WRM RDM ADM SBM
   WR0-3 RD0-3 WMP WRR RDR DCL`) — sixteen instructions, one model, and
   the addressing is the interesting part.
6. **`JMS` / `BBL` and the 3-level address stack** — the last structural
   block. `BBL` returns a value in the accumulator, which is a real trap:
   a subroutine cannot hand a result back through the accumulator because
   the return instruction overwrites it.
7. **`FIM` / `FIN` / `JIN`** — register-pair addressing, and the indirect
   forms that make data-driven jumps possible.

**Deliberately not planned:** nothing. The set is small enough to finish.

## Program store

Sizing: a 4001-equivalent **256-byte ROM is 2,048 bit sites**, which the
device model can carry. Start at 32–64 words — enough for the whole program
corpus below — and grow it once hierarchical layout exists.

The array wants to be user-editable, so a bit site is a switch the user can
flip, with the assembler as a faster way to set the same switches. Reading
the array back out gives a disassembly, so a hand-flipped bit shows up as
source immediately.

"Memory bank" is literal 4004 vocabulary, incidentally: `DCL` selects a RAM
bank and `SRC` sets the address within it.

## The assembler

The cheapest high-value piece in the project. A panel where you type 4004
assembly, which assembles in JS and **physically sets the ROM array's switch
objects**. It computes nothing the circuit would otherwise compute — it is a
loader driving real switches, the way a technician sets a plugboard, only
faster — the "simulated, never faked" rule stays intact.

One opcode table in `web/js/asm.js` (no dependencies, ~200 lines, two passes
for labels) then serves the assembler, the disassembler, the reference
emulator, and the test suite's expectations.

## Engine work that has to land first

None of this is optional at 4004 scale:

- ~~**Allocation-free conduction.**~~ **Done.** `solve()` precomputes a flat
  CSR edge list (`_eHead`/`_eNext`/`_eTo`, half-edge pairs `i`/`i^1`) once
  and a solve only writes the per-edge `_eOn` flags; floods are
  generation-stamped so no array is cleared per pass. ~2× at 4004 scale, and
  it now scales with nets *reached* rather than nets *present*.
- **Sub-circuit modules with named ports**, plus auto-routing. Hand-placing
  thousands of devices is not happening; `faCell()` and `cmosInv()` are the
  informal prototypes to formalise.
- **A block-diagram LOD tier** above the current one, where a whole module
  collapses to a labelled box showing its live bus value, with click-to-zoom
  navigation.
- **Time control.** An instruction is roughly 8 phases × 2–3 device levels.
  Even at the minimum delay that is seconds per instruction. The engine is
  already event-scheduled (`nextEventAt`), so add a turbo mode that runs
  event-to-event decoupled from rAF, plus step-by-event, step-by-cycle and
  step-by-instruction.
- **Charge decay**, if the authentic PMOS 4004 is ever the goal — its
  registers are dynamic, which is why the real chip has a *minimum* clock
  frequency. Building the architecture in static CMOS first avoids needing
  this at all.

## Testing at this scale

Exhaustive sweeps die here — you cannot enumerate a CPU's input space the
way the 8-bit adder sweeps all 131,072 combinations. Three replacements:

1. **Per-module truth tables**, as today (ALU, decoder, register file, ROM
   read).
2. **A reference 4004 emulator, in the test file only, as an oracle.** Run
   programs on both the device-level machine and the emulator and assert
   agreement *after every instruction* — per-instruction comparison
   localises a fault to one opcode instead of "the program came out wrong".
   It lives only in `test/`, so the app still conducts current for real.
3. **Fuzzing.** Random instruction sequences from a safe subset, run on
   both, diffed. Hand-written programs exercise the paths you thought
   about; a sneak path in the register-file select tree shows up on the
   instruction pair nobody would write.

## Program corpus

The programs are not an afterthought — at this scale they *are* the test
suite. Three limits set their shape: ROM is tens of bytes, not 4 KB;
execution is roughly half a second per instruction, so a good demo runs
20–100 dynamic instructions; and results must stay under 16 or overflow
deliberately so that the carry lamp is the point.

The 4004 has no HLT. The convention is a `JUN $` spin at the end, with the
harness stopping when the PC repeats with no state change.

### Bring-up ladder

These run on incomplete hardware and are how you find out the machine is
alive at all:

- [x] **P0 — fetch works.** *Fetch Machine* — PC, ROM, instruction
  register, decoder. *Sequenced Machine* adds the phase ring and a control
  unit, so an instruction holds still across FETCH/DECODE/EXEC.
- [x] **P1 — the write path.** *Accumulator Machine* — LDM loads the
  accumulator, so state changes. *Jump Machine* makes the PC loadable, so
  JUN actually jumps rather than the counter wrapping by accident.
- [x] **P2 — a single ADD.** *Adding Machine* — the real `ADD r` datapath:
  register file addressed by OPA, ripple adder, carry flag that ADD both
  reads and writes.
- [x] **P3 — one taken and one untaken JCN.** *Conditional Machine* — the
  condition tree, swept over all 128 mask/state combinations against the
  real semantics, plus the TEST pin as an actual switch.

What is still missing before the program corpus runs: two-byte fetch (so
JCN and JUN take a real address operand rather than the low bits of their
own byte), `ISZ`, `XCH` reading the register file back into the
accumulator, and the 12-bit PC wired in place of the 3-bit demo one.

### Count-up (5 bytes)

The "hello world". Watch a register count in binary; the ripple is visible.

```
        LDM 0
        XCH 0
loop:   INC 0
        JUN loop
```

### Multiply 3 × 4 by repeated addition (12 bytes, ~25 instructions)

The Busicom-flavoured one, and the best single demo. Exercises `FIM`, the
ALU and `ISZ`.

```
        FIM 0P, 3, 12   ; R0 = 3 (multiplicand), R1 = 12 (= 16−4; ISZ counts up)
        LDM 0
        XCH 2           ; product = 0
loop:   CLC
        LD  2
        ADD 0
        XCH 2
        ISZ 1, loop
        JUN $           ; R2 = 12
```

### Fibonacci (13 bytes, ~48 instructions)

The swap falls out of `XCH`. Running seven iterations makes term 8 (21)
overflow the nibble, so the demo ends by lighting the carry lamp.

```
        FIM 0P, 0, 1
        LDM 9           ; 16 − 7
        XCH 2
loop:   CLC
        LD  0
        ADD 1           ; ACC = a+b
        XCH 1           ; R1 = a+b, ACC = b
        XCH 0           ; R0 = b,   ACC = a
        ISZ 2, loop
        JUN $
```

### Subroutine nest

The 3-level address stack is a large block that nothing else touches, so it
needs its own programs — two of them.

```
        LDM 3
        XCH 3
        JMS dbl
        JMS dbl         ; R3 = 12
        JUN $
dbl:    JMS add3
        BBL 0
add3:   CLC
        LD  3
        ADD 3
        XCH 3
        BBL 0
```

…plus a deliberate **four-deep call**, because the real 4004 silently
overwrites the bottom of its 3-level stack rather than trapping. That is
authentic hardware behaviour, it is a test the reference emulator must match
exactly, and it is the kind of thing a hand-built implementation gets wrong
quietly.

Worth encoding as its own test: **`BBL` loads the accumulator with its data
field**, so a subroutine cannot return a value in ACC — it has to hand it
back through a register. Easy to get wrong in both the hardware and the
emulator.

### RAM round-trip

`DCL` / `SRC` / `WRM` / `RDM`: write a nibble, read it back, add it. The
only program that exercises the memory-bank addressing path end to end.

### Carry showcase

`LDM 15 / IAC`, tying the CPU back to the ripple-adder demo.

### Where they live

`web/js/programs.js` — assembly source as strings, shared by the app and the
tests. The CPU's registry entry gets a program picker; selecting one
assembles it into the ROM's switch objects, so the demo and the test load
the same bytes into the same hardware.

## Staging

Every stage ships something usable on its own, so the library keeps growing
while the CPU is built.

- [x] **0. Engine** — fast conduction (CSR edge list, generation-stamped
      floods), sub-circuit modules with named ports, a clock with run /
      pause / step. Auto-routing and a block-diagram LOD tier are still
      open but have not blocked anything.
- [x] **1. Datapath parts as library circuits** — ALU, program ROM in two
      technologies, 16×4 register file, program counter (loadable),
      instruction decoder. All in the picker, each usable alone.
- [x] **2. Disassembler** — sharing the decoder's opcode table, so a
      program listing and the lit decoder line cannot disagree. The
      assembler direction is still open.
- [x] **3. Control sequencing** — the ring counter, hardwired control unit,
      condition tree, and two-byte fetch. This was flagged as "the hard
      part, and where machines like this stall"; it did not stall, because
      the module abstraction from stage 0 landed first as planned.
- [ ] **4. Integrate** — one machine with the full instruction set, running
      the program corpus, cross-checked against the reference emulator.

The risk recorded here was that step 3 depended entirely on the module
abstraction from step 0. That proved right and was handled by doing the
performance and module work first; worth keeping as a record of a call that
paid off.

What is left is mostly instruction-set coverage rather than new structure —
see the checklist above. The one structural piece remaining is the 3-level
address stack that `JMS` and `BBL` need.

## The machines built so far

Each isolates one idea, and each is in the picker under CMOS · Machines.
They are teaching steps rather than drafts: the fetch machine is still the
clearest place to see a fetch, precisely because nothing else is happening
in it.

| machine | what it added |
|---|---|
| Fetch Machine | PC → ROM → instruction register → decoder |
| Sequenced Machine | phase ring and a control unit; an instruction holds still across its phases |
| Accumulator Machine | state that changes — LDM writes the accumulator |
| Jump Machine | a loadable PC, so a decoded jump actually jumps |
| Adding Machine | the real `ADD r` datapath: register file, adder, carry flag |
| Conditional Machine | the JCN condition tree, and the TEST pin |
| Two-Byte Machine | two-byte fetch; the jump target stops being welded to the opcode |
| Accumulator Group | the 1111 escape decoded a second time; a five-way source mux, and rotates through the carry |
